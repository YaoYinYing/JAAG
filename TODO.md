# BioNuTA — Workbench modernization and embeddable input builder

Temporary execution checklist for this PR. Product name: **BioNuTA — Biomolecular Input Assembler** (formerly JAAG). Product promise: **Assemble once. Model anywhere.**

## Outcome and scope

Turn JAAG into BioNuTA: a modern, model-agnostic biomolecular input workbench with one maintained editor, versioned restorable scientific authoring state, and a small host-neutral embedding interface. A host such as REvoCompute must be able to bind a user's edits directly to target-native Task inputs and restore those edits for Clone & Reuse without a manual download/upload round trip.

This PR delivers the BioNuTA repository side only. REvoCompute's generic Input Builder lifecycle, Task persistence/authorization and AtomWorks Studio/RFD4 adapter belong in REvoCompute. BioNuTA is a shared/public builder (multiple runner targets), while a runner-specific/private builder could wrap unmodified AtomWorks Studio. These categories are about scope, not permission to disclose data. Do not change REvoCompute, fork Studio, invent a common molecular schema across builders, or implement a scheduler.

## 3. Host-neutral Input Builder interface

- [ ] Specify a minimal, versioned contract; illustrative names: mount, snapshot, restore, validate, materialize, subscribe/change, destroy. Mount receives host-declared target and configuration; standalone permits target selection. Embedding must use the full workbench UI, not a simplified second editor. Support multiple isolated instances or document and enforce a single-instance limitation.
- [ ] Provide a typed/documented buildable adapter and reference host harness that exercises the actual public interface. Choose a small module/custom element or an isolated iframe/message-bridge based on actual architecture and compatibility; document tradeoffs. The core contract is transport-independent. Do not bind the canonical editor to a REvoCompute global.
- [ ] Define snapshot envelope fields (builder identifier/version, document schema version, target, editable state, dependencies) and materialization result (role/logical slot or host mapping, safe filenames, MIME/bytes, diagnostics, state revision and output binding/digest evidence). Keep scientific content distinct from provenance. The host owns input roles, authorization, acceptance/storage, Task identity and execution; BioNuTA never submits a job. Avoid a new plugin framework.
- [ ] Host receives change notifications and can validate/materialize without user download. Bind generated outputs only through host APIs. Reject stale async results; when edits invalidate a generated output, mark/remove only builder-owned output, never overwrite an independent upload. No automatic submission. Capture snapshot and outputs for the same revision; no false claim that mismatched bytes can reproduce the edit.
- [ ] Handle mount/ready, restore-before-edit, errors, cancellation, destruction, teardown of listeners, timers, object URLs and outstanding operations. Fail explicitly if builder unavailable; host can fall back to ordinary uploads. If iframe transport, validate exact origin, source, instance/handshake and message schema, enforce bounds, avoid wildcard targetOrigin for scientific payloads and prevent replay/cross-instance mixups. No credentials in builder documents.
- [ ] Embedded mode hides standalone-only navigation/share/download controls as appropriate; target is fixed by host; never put private input in URL/history/analytics/local persistent browser state by default. Keep standalone share/import/download and legacy compressed links functional; clearly identify explicit share as non-private. No silent remote transfer of user data (including glycan lookup); make any existing external lookup explicit and document what is sent.
- [ ] Demonstrate a real host harness preparing at least AF3, OpenDDE and BioEmu2, receiving inputs, storing snapshot/dependency metadata, destroying/recreating the editor, restoring and editing the clone, then materializing equivalently. Cover dependency resolution, mismatch/invalid state, target or version incompatibility, missing assets, and external-upload ownership. This is a host-neutral Clone & Reuse simulation, not a claim that REvoCompute production is integrated.
- [ ] Update integration docs with copyable host examples, lifecycle and event semantics, privacy, compatibility/versioning, assets/build commands, errors and downstream mapping. Keep legacy integration compatible where consumed or supply an explicit tested compatibility shim. Rebuild official artifacts from source; never hand-edit dist.
